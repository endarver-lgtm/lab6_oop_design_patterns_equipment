## Проблема виртуального конструктора в C++

Ключевой теоретический вопрос лабораторной работы – запрет на виртуальные конструкторы в спецификации стандарта C++.

Причины носят фундаментальный характер:
1. **Объект еще физически не существует**: виртуальный вызов опирается на указатель на таблицу виртуальных методов (`vptr`), находящийся внутри заголовка объекта. До вызова конструктора память под объект не инициализирована, указатель `vptr` не настроен.
2. **Размер типа неизвестен на этапе компиляции**: для выделения стекового фрейма или блока динамической памяти компилятор обязан точно знать `sizeof(T)`. Если бы конструктор был виртуальным, вызывающая сторона не могла бы знать размер конкретного производного класса.
3. **Порядок инициализации иерархии**: конструирование в C++ идет строго сверху вниз (от базового класса к наследникам). Виртуальный механизм же направлен на вызов наиболее глубокого переопределения снизу вверх, что привело бы к обращению к неинициализированным полям производного класса.

В то же время **деструктор полиморфного базового класса обязан быть виртуальным**: при удалении объекта через указатель на базовый тип `delete basePtr` только виртуальный деструктор гарантирует корректный вызов деструкторов производных классов и освобождение всех динамических ресурсов.

## Обзор 5 реализованных паттернов конструирования

Для обхода невозможности создания виртуального конструктора в проекте реализованы 5 альтернативных шаблонов:

```
           ┌─────────────────────────────────────────────────────────┐
           │     Проблема: конструкторы в C++ не виртуальные         │
           └────────────────────────────┬────────────────────────────┘
                                        │
    ┌──────────────────┬────────────────┼─────────────────┬──────────────────┐
    ▼                  ▼                ▼                 ▼                  ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  Паттерн 1   │ │  Паттерн 2   │ │  Паттерн 3   │ │  Паттерн 4   │ │  Паттерн 5   │
│ Фабричный    │ │ Параметризо- │ │ Фабричный    │ │ Полиморфная  │ │ Полиморфное  │
│ метод        │ │ ванная       │ │ конструктор  │ │ фабрика с    │ │ клонирование │
│ (Factory     │ │ фабрика со   │ │ (Dynamic     │ │ ковариантным │ │ через CRTP   │
│  Method)     │ │ спец-иями    │ │  Registry)   │ │ возвратом    │ │ (Prototype)  │
└──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘
```

### 1. Классический фабричный метод (Factory Method)
Базовый класс создателя `EquipmentFactory` декларирует чистый виртуальный метод:
```cpp
virtual std::unique_ptr<ConstructionEquipment> createEquipment(int id, ...) const = 0;
```
Конкретные фабрики (`ExcavatorFactory`, `CraneFactory`, `BulldozerFactory`, `DumpTruckFactory`, `ConcretePumpFactory`) переопределяют этот метод, создавая соответствующий экземпляр. Клиентский код работает исключительно через полиморфную ссылку на фабрику.

### 2. Параметризованная фабрика со спецификациями (`EquipmentSpecs.h`)
Разные виды спецтехники требуют принципиально разных характеристик при рождении. Вместо антипаттерна передачи длинного списка бессмысленных `void*` или десятков необязательных параметров, создана иерархия структур спецификаций:
* `ExcavatorSpec`: объем ковша, глубина копания, тип шасси;
* `CraneSpec`: грузоподъемность, вылет стрелы, высота подъема;
* `BulldozerSpec`: ширина отвала, тяговый класс, тип рыхлителя;
* `DumpTruckSpec`: грузоподъемность кузова, число осей;
* `ConcretePumpSpec`: длина распределительной стрелы, подача бетона м³/ч.

### 3. Фабричный конструктор (Dynamic Type Registry)
Класс `EquipmentRegistry` моделирует динамический реестр типов. Вместо монолитного оператора `switch/case` создатели регистрируются в ассоциативном словаре:
```cpp
std::unordered_map<std::string, std::function<std::unique_ptr<ConstructionEquipment>(...)>> creators_;
```
Добавление шестого типа машины не требует изменения кода существующих модулей диспетчеризации (соблюдение *Open-Closed Principle*).

### 4. Полиморфная фабрика со связанными сущностями и ковариантным возвратом
Каждая единица спецтехники агрегирует совместимое навесное оборудование (`Attachment`). Фабрики создают комплектные рабочие станции: экскаватор комплектуется ковшом либо гидромолотом, кран – грузозахватным крюком или электромагнитом. Используется механизм ковариантных типов возврата C++.

### 5. Полиморфное глубокое копирование через идиому CRTP
Паттерн «Прототип» (виртуальный конструктор копирования) реализован через метапрограммирование с помощью идиомы *Curiously Recurring Template Pattern*.

## Идиома CRTP и шаблонный Cloner

Классическая реализация виртуального конструктора копирования требует вручную прописывать метод `clone()` в каждом классе:
```cpp
virtual ConstructionEquipment* clone() const override {
    return new Excavator(*this);
}
```
При разрастании иерархии это приводит к копипасте и риску опечатки в типе.

В данном проекте применена элегантная идиома CRTP (`Cloner.h`):

```cpp
template <typename Derived, typename Base = ConstructionEquipment>
class Cloner : public Base {
public:
    using Base::Base; // Наследование конструкторов базового класса

    std::unique_ptr<ConstructionEquipment> clone() const override {
        return std::make_unique<Derived>(static_cast<const Derived&>(*this));
    }
};
```

Теперь любой класс объявляется одной выразительной строкой:
```cpp
class Excavator : public Cloner<Excavator, ConstructionEquipment> { ... };
```
Компилятор сам генерирует строго типизированный полиморфный метод клонирования.

## Динамический реестр типов (EquipmentRegistry)

Модуль `EquipmentRegistry` обеспечивает слабую связанность между интерфейсом диспетчера и конкретными производными классами:

```cpp
class EquipmentRegistry {
public:
    using CreatorFunc = std::function<std::unique_ptr<ConstructionEquipment>(const EquipmentSpec&)>;

    static EquipmentRegistry& instance();
    void registerType(const std::string& typeName, CreatorFunc creator);
    std::unique_ptr<ConstructionEquipment> create(const std::string& typeName, const EquipmentSpec& spec) const;
    std::vector<std::string> getRegisteredTypes() const;
};
```

Благодаря паттерну Singleton и лямбда-фабрикам создание новых типов техники регистрируется при запуске программы динамически.

## Архитектура фасадного менеджера парка

Класс `EquipmentManager` скрывает детали хранения полиморфных объектов:
* Хранилище: `std::vector<std::unique_ptr<ConstructionEquipment>> fleet_`;
* Поддержка умных указателей `std::unique_ptr` гарантирует автоматическое освобождение памяти без утечек при удалении или перезаписи машин;
* Поддерживает полный жизненный цикл данных: полиморфное добавление, удаление, редактирование реквизитов, сквозной расчет суммарной стоимости аренды парка и экспорт сводных ведомостей в файл.
